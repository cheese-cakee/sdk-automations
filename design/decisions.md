# Decision and Evidence Register

> This register separates principles that current evidence supports from hypotheses that still need
> maintainer review or sandbox experiments. A document does not become approved merely because it appears in
> this repository or in pull request 23.

## 1. Status meanings

The register uses the following status values.

| Status | Meaning |
|---|---|
| `supported` | The audits, accepted proposal, and current research are strong enough to guide the next work. |
| `hypothesis` | The idea is technically plausible, but maintainers or experiments must still confirm it. |
| `reopened` | New evidence has challenged an earlier proposal, so it must not guide implementation yet. |
| `ratified` | Maintainers have explicitly approved the decision and recorded the date and evidence. |
| `replaced` | A later decision has replaced the earlier proposal. |

## 2. Supported product principles

| Identifier | Principle | Evidence |
|---|---|---|
| P1 | The product is one hosted GitHub App with repository-selected capabilities. | The accepted proposal and `planning/goals.md` support this direction. |
| P2 | A repository must explicitly enable every workflow-changing capability, and every user-facing capability defaults to off. | Maintainer consent and the different C++, Python, and JavaScript workflows require explicit opt-in. |
| P3 | A capability does not call or import another capability. | The coupling audit shows that direct and hidden sibling contracts are difficult to test and change. |
| P4 | A capability receives only its own configuration and a narrow platform interface. | The C++ shared-config coupling and GitHub API mock drift support a smaller boundary. |
| P5 | GitHub remains authoritative for visible repository facts. | Labels, assignees, reviews, comments, and open or closed state must continue to reflect human edits. |
| P6 | The design does not assume that GitHub alone stores every operational recovery record. | Webhook delivery, multi-call recovery, and coordination require feasibility experiments. |
| P7 | Repository labels and fields are mappings or profile defaults rather than universal platform strings. | The three audited SDKs use materially different workflow models. |
| P8 | Testing begins with a development App and personal sandbox before any Hiero repository receives writes. | The permission and failure risks require an isolated validation path. |
| P9 | A production webhook receiver durably accepts work before it acknowledges the delivery. | GitHub requires a quick response and does not automatically redeliver every failed delivery, so an acknowledged in-memory event cannot provide reliable recovery. Demonstrated in the sandbox (experiment 6.2, 2026-07-23): a crash after acknowledgement but before durable acceptance lost the delivery while GitHub's ledger recorded success; an ack-first relay in the transport path recreates the same loss window with no crash at all. |

### Hypotheses surfaced by the pure-logic implementation

Coding the design prose into the implementation packages (`core/`, `store/`, `executor/`) forced
ambiguities into concrete choices. Each choice is tagged `FINDING(...)` in the source at the exact place the assumption was made, and
the invariant tests in `core/test/` exercise the chosen behavior. The code is evidence that the choice is
*coherent*, not that it is *right* — each row still needs the named review.

| Identifier | Choice the code had to make | Current status | Required next evidence |
|---|---|---|---|
| D28 | `blocked` is an orthogonal pause flag, not a workflow position: an item keeps its position while blocked, and unblocking restores it unchanged. `taxonomy.md` §2 lists `blocked` as a meaning, but neither state diagram contains it, and `safety.md` treats it as a pause. (`core/src/taxonomy.ts`, `FINDING(taxonomy-blocked)`.) | `hypothesis` | Maintainers must confirm the flag model when reviewing the workflow profile, or the diagrams must gain explicit `blocked` positions. |
| D29 | Manual entry into any state is recorded as observed reality to reconcile, not as a requestable transition: the exhaustive transition matrix rejects module requests for edges the diagrams do not contain, while human edits may still land anywhere. The prose rule "every state has a non-module way in" implies edges the diagrams omit. (`core/src/taxonomy.ts`, `FINDING(taxonomy-manual-entry)`.) | `supported` | The manual-edit scenarios under D6/D8 must confirm reconciliation matches maintainer expectations for each profile state. |

(`core/src/safety.ts`, `FINDING(safety-grace-floor)`.) | `hypothesis` | Maintainers must ratify the floor value (or a different one) when the first destructive capability is reviewed under D10. |

(`core/src/config.ts`, `FINDING(config-no-config-mode)`.) | `hypothesis` | The configuration review under Q14 must confirm the mode name. | D32 | The stage-three feasibility experiments (build plan §6.1–§6.6) are capability-independent and may run while the stage-two capability-ranking gate is still open. | D33 | The rule-5 comparison lives in the core, and an exact-timestamp tie goes to the human: `evaluateWrite` refuses when the newest human change on the touched state is at or after the request's `causeObservedAt` (`>=`, not `>`), with the shell required to exclude the causing event itself when supplying `latestHumanChangeAt` — a human edit that both triggers the request and is the newest touch is the cause, not a conflict. A same-entity-only rule (`ready` and `needsReview` sharing one "attention" label, disambiguated by entity) would be a deliberate relaxation. (`core/src/config.ts`, `FINDING(config-label-injectivity)`.) | `hypothesis` | The configuration review under Q14 must define "incompatible" — confirm full injectivity or ratify the same-entity relaxation. |
| D35 | The observation projection's three readings, encoded together in `core/src/observe.ts`: a position meaning of the other entity's flow observed on an item is left alone and reported as ignored, never a conflict (`FINDING(observe-cross-entity)` — `manual-edits.md` §3 rule 1's "unrelated labels" read to cover the other flow); `blocked` with no position is a legal observation projecting to "no position, paused" (`FINDING(observe-blocked-alone)` — D28's orthogonal flag applied at the observation boundary); and a closed item keeps whatever position labels it carries, unrepaired, with the state machine's closed guard refusing transitions regardless (`FINDING(observe-closed-position)` — silence on closure per `manual-edits.md` §6). | `hypothesis` | The D6/D8 manual-edit scenario review confirms all three readings together; the blocked reading ratifies or falls with D28. |

| D37 | Folded into D35 (2026-07-25): closed items keep their position labels. | `replaced` | See D35. |
| D38 | Fail-closed validation is whole-file: one error anywhere yields no configuration, dropping the repository to `observe` and stopping every working capability until the file is fixed. Last-known-good was rejected because an older automation decision must not outlive a newer human edit (a maintainer's attempt to disable a behavior would fail while the behavior keeps running); partial salvage was rejected because an uninterpretable fragment can change the meaning of valid-looking fragments (the reason §2.7 rejects unknown keys) and a half-running state is the hardest to debug. The loud full stop is acceptable maintainer experience only with two shell-owned mitigations: the configuration report (`projections.md` §3) within seconds of the breaking edit, and PR-time validation as a check run on any PR touching the file, so invalid configuration normally never reaches the default branch. (`core/src/config.ts`, `FINDING(config-fail-closed-granularity)`.) | `hypothesis` | Maintainers must confirm the full-stop-with-report experience during the ring-one pilot (Q8), and the PR-time validation check must exist before any repository runs `active`. |
| D39 | An active kill switch refuses even pure observations: the kill-switch check precedes the observation short-circuit in `evaluateWrite`, so "stop" means stop reading-and-recording, not merely stop writing. `safety.md` §5 does not say which reading wins; the total stop is encoded because a kill switch is an operator's emergency brake, and residual activity after pulling it costs trust exactly when trust is lowest. The rest of the check order carries no outcome semantics — it only decides which machine-readable `code` is reported when several rules fail at once, and the verdict-code tests freeze that reporting order as contract. (`core/src/safety.ts`, `FINDING(safety-killswitch-observations)`.) | `hypothesis` | The kill-switch design under D22 must confirm the total-stop semantics — in particular whether operator alerts and security controls (which `manual-edits.md` §5 exempts from an item-level block) are also exempt from a kill switch, which this code does not model. |
| D40 | Body-regex failure classification is snapshot evidence, not contract: the rules in `core/src/failures.ts` match prose GitHub sent on 2026-07-23, and GitHub may reword it at any time. The mitigation is structural plus operational: an unrecognized 403 degrades into the explicit `forbiddenUnrecognized` class carrying the body verbatim (never a fabricated diagnosis), and a periodic sandbox re-probe must re-validate the observed fixtures — a rise in `forbiddenUnrecognized` operator reports is the signal that the catalogue needs a new observation run. (`core/src/failures.ts`, `FINDING(failures-prose-snapshot)`.) | `supported` | The operations review under Q1/Q13 must schedule the re-probe cadence and name the owner of fixture refresh. |
| D41 | Effect claims are leases, not permanent locks: `claim` atomically takes over a claim whose timestamp is at or before the caller's stale threshold (one upsert — no delete-then-claim race window), and `release` removes only the holder's own row on clean completion, so a crash while holding a claim cannot deadlock the effect. A lease can therefore be stolen from a live worker whose call outlives it — accepted because claims are contention optimization, not correctness: the journal plus GitHub re-read (D24's replacement loop) remains the duplicate-prevention layer, as 6.5 demonstrated. The lease duration must exceed the longest plausible effect and is an operations decision, not a code constant. (`store/src/store.ts`, `FINDING(store-claim-lease)`.) | `supported` | The stage-four storage ratification must set the lease duration and confirm the stolen-lease scenario is exercised by the executor's resolver tests. |
| D42 | The effect journal carries a durable per-call `attempt` counter, and a `done` row is immutable to `intent`: re-declaring a still-open call increments the counter in the same single-statement upsert, while acknowledged history can never regress to `sent` (the original `INSERT OR REPLACE` could silently un-happen a receipt, sending recovery to re-resolve completed work). This amends the ratification-pending four-table schema by one column, implementing the storage decision's own "retries with bounded history" cell — which the decided schema claimed but did not support — and making retry bounds (core's `MAX_RATE_LIMIT_ATTEMPTS`) survive restart instead of resetting with the process. A count, not per-attempt rows: forensic history was not demanded by any 6.5 recovery. Pre-ratification store files are not migrated. (`store/src/store.ts`, `FINDING(store-journal-attempts)`.) | `supported` | The stage-four storage ratification reviews the amended `effect_journal` schema alongside the original four-table decision. |
| D43 | The reconciliation sweep the design leans on (D18) has a concrete store API: `schedule` gains a `claimed_at` column stamped by `claimDue`, `requeueStuck(claimedBefore)` atomically returns stuck `running` rows to `pending` (stuckness judged by claim age, never due time, so a backlog catch-up is not stolen from; requeued work re-fires through the normal `claimDue` path — no parallel firing mechanism), and `openIntents(before)` lists every unresolved `sent` journal row as the recovery loop's worklist. A slow-but-alive schedule handler can be requeued and fire twice — accepted on D41's grounds: the journal plus GitHub re-read is the duplicate-prevention layer. The requeue threshold is the sweep's operations decision, as is retention: `seen_delivery`, `done` journal rows, and released-claim leftovers grow without bound until the sweep design names pruning windows (the deliveries API's own retention is thirty days; the store's must be decided, not defaulted). (`store/src/store.ts`, `FINDING(store-sweep-api)`.) | `supported` | The stage-four storage ratification reviews the amended `schedule` schema, and the sweep design under D18 sets the requeue threshold, retention windows, and D41's lease duration together. |
| D44 | A call re-sent `MAX_CALL_ATTEMPTS = 5` times without a confirmed outcome stops retrying and surfaces to the operator as unresolved. The storage decision requires "retries with bounded history" but names no bound — the same unnamed-limit pattern as the grace-period floor (D30). The bound reads the journal's durable attempt counter (D42), so it survives restarts; the crash grid demonstrates convergence well inside it. (`executor/src/recovery.ts`, `FINDING(executor-attempt-bound)`.) | `supported` | The stage-four storage ratification confirms the bound value alongside D42's counter. |
| D45 | An open journal row that no longer matches the current plan (seq beyond the plan, or a different intent at that seq) surfaces as unresolved and is never remapped: `manual-edits.md` §9 rules that intents created under an old configuration revision are invalid, so the executor stops rather than guess a correspondence between old and new plans. (`executor/src/recovery.ts`, `FINDING(executor-stale-plan)`.) | `supported` | The configuration-revision design under Q14 must define how surfaced stale effects are closed out (operator action, automatic abandon after review, or re-issue under the new revision). |
| D46 | The recovery loop's exactly-once guarantee is proven only relative to a CONSISTENT read-back: the crash grid's fake world answers `readBack` with perfect read-after-write consistency, but real GitHub reads can lag writes, and a stale "absent" immediately after a landed create would make the loop duplicate despite following every rule. The loop is correct given the precondition; the precondition is not free. The real port owes a confirmed-fresh read (or a bounded delay and re-read) before answering "absent". (`executor/src/recovery.ts`, `FINDING(executor-readback-consistency)`; the harness declares where its world is kinder than GitHub.) | `supported` | The stage-five adapter sandbox must measure read-after-write staleness for every resolver read the first capability uses (starting with list-comments after create-comment), and the port must encode the resulting freshness rule before this row can ratify. |

## 5. Ratification rule

A hypothesis becomes `ratified` only after the register names the approving maintainers, the date, and the
evidence they reviewed. A sandbox result may reject a hypothesis without selecting the final replacement.
When that happens, the row becomes `reopened` until a later decision is ready.

[`ratification-packet.md`](ratification-packet.md) collates every currently pending row into per-venue
agendas with recommended answers — the stage-four working document. Outcomes land back here, not there.
