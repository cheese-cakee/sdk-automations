# 8.7 — recover a backed-up store

## Question

Can the operator restore a store, explain its recorded decisions, and resume the work that copy
remembers without duplicating a confirmed landed effect? What history does an older copy lose?

## Offline proof

From the repository root, with dependencies installed:

```bash
pnpm --filter @hiero-hackers/automation-runtime exec vitest run test/shell/compose/recovery.test.ts
```

The test takes a real SQLite backup, closes the source, opens the copy as a `Store`, and uses the
existing shell and applier. Deliveries use the scrubbed `issues.opened` capture; the effect cases
use the existing synthetic GitHub that remembers writes. Its injected interruptions and failed
reads are explicit in each test. No GitHub credentials or live writes are involved.

| Case | Required result |
|---|---|
| completed delivery | decisions, status and item explanation survive; redelivery is a duplicate; different bytes conflict; no new decision |
| copied delivery lease | unchanged payload bytes and digest; no takeover before expiry; a new token after expiry; old token cannot release the new claim; drain completes once |
| interrupted send before GitHub changed | copied open send is retained; confirmed absence permits one successful retry |
| interrupted send after GitHub changed | copied open send resolves through read-back; no second comment write |
| unreadable comment list | no write and send remains open; a later successful read resolves it |

This proves the backup/reopen path with simulated GitHub, not the pilot host, network, operator,
storage retention or disaster recovery. Existing store backup tests separately show that a delivery
accepted after the backup is absent from the copy.

## Operator rehearsal, before a hosted pilot

Use an approved repository in `observe`. Record the candidate commit, host, operator, repository,
configuration revision, store path, backup completion time and backup size. Keep secrets separate
from the store and evidence. No host or repository is approved by this protocol.

1. Stop the original process gracefully and confirm its exit, so neither intake nor in-flight
   processing changes the checkpoint. Run `pnpm shell:status` and
   `pnpm shell:explain --item issue#<number> --repo <owner/repo>`
   for a recorded item. Take `pnpm shell:backup <unused-backup-path>`, wait for success, and
   preserve that completed copy. The backup API also works on an open source, but concurrent
   processing can legitimately change its rows during a backup; this drill needs a fixed checkpoint.
2. Keep the original stopped and its store preserved for reconciliation. Place a
   copy of the backup at a different, empty recovery path. Start the same version on an unrouted
   loopback port, with `STORE_PATH` set to that path, config in `observe`, `APP_SLUG` absent,
   and no sweep. Confirm `/readyz` and record startup/drain logs.
3. Compare the recovered delivery counts, decisions and explanations to the checkpoint. Account
   for each pending or processing delivery as it completes or reports a refusal. Compare open
   sends separately: disarmed observe recovery is not proof of active effect recovery.
4. Identify deliveries accepted after the checkpoint using the preserved source and GitHub's
   delivery log. An old backup may omit both a delivery and its effect journal. Request approved
   redelivery while available, recording GUIDs and outcomes; do not enable writes to repair an
   uncertain history. GitHub does not automatically redeliver failed webhooks.
5. Stop the rehearsal instance before restarting the original or routing intake to the recovered
   one. There must be one receiver and one writer for the installation. Record the recovery time,
   missing history, reconciled outcomes, chosen store and rollback result in the pilot issue.

A successful rehearsal requires matching checkpoint evidence, explained queued work, preserved
uncertainty, and one active process. Report missing history honestly: a completed SQLite backup
is a consistent copy, not an external-effect checkpoint. This protocol grants no active writes.

References: [SQLite backup API](https://www.sqlite.org/backup.html),
[Node's backup API](https://nodejs.org/api/sqlite.html#sqlitebackupsourcedb-path-options),
and [GitHub redelivery guidance](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks).
