# 6.8 Linked-issue semantics (D123)

`readLinkedIssues` had no operation row in the endpoint-permission matrix. A
row without a citation is a guess, and this is the read the `linkedIssues`
resolver answers from. The audit found the existing bots answer
"what issue does this PR close?" two different ways that can disagree (B2), so
the question is not only whether GitHub answers it but which answer we adopt.
The observations below now supply that missing evidence.

## Question

For a pull request in the sandbox, what does GraphQL
`closingIssuesReferences(excludeUserLinked: true)` return — and how does it
differ from what a maintainer would call a link?

GitHub documents that the unfiltered field may include issues linked through
the UI. The platform asks about closing references, so every probe uses
`excludeUserLinked: true`. A plain mention and a manual link are separate cases.

## Method

Use three private personal sandbox repositories. The App installation includes
the source repository and one target repository; the third repository remains
outside the installation. Record the raw response locally, the request id, and
the quota headers for every call. Never record an authorization header, token,
JWT, or private key.

The disposable runner belongs in ignored `harness/`, and raw responses belong
in ignored `evidence/`. It must send each request once: a retry would replace
the failure shape this protocol exists to observe.

Use this query for every valid-token case, following `pageInfo.endCursor` until
`hasNextPage` is false:

```graphql
query LinkedIssuesProbe(
  $owner: String!
  $repo: String!
  $number: Int!
  $after: String
) {
  repository(owner: $owner, name: $repo) {
    nameWithOwner
    pullRequest(number: $number) {
      number
      baseRefName
      closingIssuesReferences(
        first: 100
        after: $after
        excludeUserLinked: true
      ) {
        totalCount
        nodes { number repository { nameWithOwner } }
        pageInfo { hasNextPage endCursor }
      }
    }
  }
  rateLimit { cost limit remaining used resetAt }
}
```

1. **Keyword close** — open a PR whose body says `Closes #N`. Query
   `closingIssuesReferences`. This is the baseline: it must return N.
2. **Manual mention** — a PR body that says `related to #N` and `see #N`, with
   no closing keyword. Record whether N appears. Separately link an issue using
   GitHub's UI and confirm that `excludeUserLinked: true` excludes it. The
   audit's Inactivity Reaper used a body-text regex that would match mentions;
   the merge path used closing references, which would not (B2).
3. **Cross-repository** — a PR closing an issue in a second sandbox repository.
   Use the fully qualified `Closes OWNER/REPOSITORY#N` form and target the
   source repository's current default branch. Record whether it resolves, and
   whether the installation needs access to the target. Repeat the installed-
   target query with a token restricted to the source repository, then query a
   second source PR that closes an issue in the private repository outside the
   installation.
4. **Multiple links** — one PR closing two issues; confirm ordering and that
   nothing is silently truncated.
5. **Edited after open** — open with no link, then edit the body to add
   `Closes #N`. Record whether the reference updates and how quickly, since
   the resolver reads at decision time, not at open time.
6. **Unlinked** — a PR with no references at all. Record the exact empty
   shape, so `absent` is distinguishable from a failure.
7. **Failure shapes** — repeat one query with a deliberately invalid
   installation token, and once against an existing private repository outside
   the installation. Record the HTTP status and distinguish `errors[]`, partial
   `data`, `repository: null`, `pullRequest: null`, an empty connection, and a
   transport failure. Only a present pull request with an empty connection and
   no errors is confident absence.
8. **Cost** — record `rateLimit.cost` for every page and the
   `x-ratelimit-*` response headers. The query cost is the measurement; a
   before-and-after header delta can be changed by concurrent activity.

For the permission row, mint tokens restricted to the source and installed
target repositories. Run the same cross-repository query with Issues and Pull
requests read permission, without Issues, and without Pull requests. Record the
permissions returned by each mint. This measures the minimum instead of merely
describing the App's full grant set.

## What decides what

- **Case 2 checks the platform's definition of a link.** Plain mentions are not
  closing references. GitHub documents manual links as a separate input to the
  connection; `excludeUserLinked: true` keeps them out of this resolver.
- **Case 3 decides the resolver's scope.** If cross-repository needs a grant
  outside the ceiling, the resolver is same-repository only until stage four
  reopens the ceiling.
- **Case 5 decides when the resolver may be memoized.** A reference that
  updates on edit cannot be cached across a delivery.
- **Cases 6 and 7 decide the fail-honest read.** `absent` and `unknown` must
  be different values; if their shapes are not distinguishable from the
  response, the adapter needs a rule that treats ambiguity as `unknown`.
- **Case 8 decides whether the sweep can afford it**, or whether the resolver
  is event-triggered only.

The conclusions are recorded in the endpoint-permission matrix, D123, and the
adapter guide. Together they define the safe first resolver scope.

## App-auth observations — 2026-08-30

The App was installed on the private source and target repositories, but not
the private outside repository. Two no-retry runs returned the same result in
every case. Raw responses remain in the ignored evidence directory; the
citations below are evidence-file case ids, not tracked credentials.

| Case | Result | Citation |
|---|---|---|
| Installed cross-repository target, full grants | 200, one closing issue | `2026-08-29T20-51-00.386Z#cross-repository-installed-target`; repeat `2026-08-29T20-51-32.049Z` |
| Same repository, full or source-only token | 200, one closing issue | `…T20-51-00.386Z#same-repository`, `#same-repository-source-only-token`; repeat `…T20-51-32.049Z` |
| Same repository, Issues omitted | 200, no errors, empty connection | `…T20-51-00.386Z#same-repository-without-issues-permission`; repeat `…T20-51-32.049Z` |
| Pull requests omitted | 200, `pullRequest: null`, `FORBIDDEN` error | `…T20-51-00.386Z#same-repository-without-pull-requests-permission`; repeat `…T20-51-32.049Z` |
| Unlinked control | 200, no errors, empty connection | `…T20-51-00.386Z#unlinked-negative-control`; repeat `…T20-51-32.049Z` |
| Target outside installation | 200, no errors, empty connection | `…T20-51-00.386Z#cross-repository-outside-target`; repeat `…T20-51-32.049Z` |
| Installed target omitted from token | 200, no errors, empty connection | `…T20-51-00.386Z#cross-repository-source-only-token`; repeat `…T20-51-32.049Z` |
| Source outside installation | 200, `repository: null`, `NOT_FOUND` error | `…T20-51-00.386Z#outside-installation-source`; repeat `…T20-51-32.049Z` |
| Invalid bearer value | 401, `Bad credentials` | `…T20-51-00.386Z#invalid-token`; repeat `…T20-51-32.049Z` |

Every valid GraphQL request cost one point. The installation-token mint
confirmed `metadata: read`, `issues: read`, and `pull_requests: read`; the
restricted tokens confirmed each omitted grant and repository scope.

The first setup run also requested `defaultBranchRef`, which produced an
unrelated permission error in every otherwise-valid case. The field was
removed before the two recorded runs: each fixture's base branch had already
been checked when it was created, and the linked-issue operation does not need
repository branch metadata.
