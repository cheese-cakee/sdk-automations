# 8.6 The triage queue on real issues

Run on 2026-09-19 against the lead's sandbox, App `4377258`, installation `148563067`, from the
branch under review with writes armed. Protocol 6.15 had proved the two lock endpoints; this run
drove the quarantine flow through the shell with real deliveries, and found that no label can
release the lock on today's platform.

## Question

That a new issue is labelled, welcomed and locked in that order from one `opened` delivery; that
a person's `ready` unlocks it, with the triage label still on; that a redelivery duplicates
nothing; that an issue a template already labelled is welcomed and locked without a second label;
what the platform does when `blocked` sits on a locked issue and `ready` arrives; and whether a
locked issue's author can still edit its title and body — the fact phase 3's needs-more-information
outcome depends on.

## Red line

The lead's sandbox only; issues the lead opens for the purpose, and one opened from an account
with no access to the repository, for the edit question. The configuration enabling `triageQueue`
in `active` goes on the default branch by the lead's own credentials for the run and is restored
after. Label, comment, lock and unlock writes on the fixtures only. Every fixture is unlocked and
closed before cleanup. The store is a fresh file under the scratch directory.

## Method

The shell from the branch under test with `APP_SLUG` set (writes armed), behind the smee relay 8.1
accepted, `TICK_SECONDS=20`, no sweep cadence.

```yaml
capabilities:
  triageQueue:
    enabled: true
    welcome: true
    lockUntilTriaged: true
    confirmUnlock: true

mappings:
  labels:
    awaitingTriage: "status: triage"
    ready: "status: ready for dev"
```

| Fixture | Made by | Opened as |
|---|---|---|
| A | the lead | plain, no labels |
| B | the lead | plain, no labels |
| C | the lead | already carrying `status: triage` from an issue template |
| D | an account with no repository access | plain, no labels |

Steps, each a delivery unless it says otherwise:

1. Open A. Expect three writes in order — label, welcome, lock — and the App's own `labeled` and
   `locked` deliveries decided without action.
2. Redeliver A's `opened` from the App's ledger. Expect `deliveryDuplicate`, zero writes.
3. On A, add `status: ready for dev` with `status: triage` still on. Expect the unlock and the
   confirmation, and the decision rows naming the two-position conflict without a refusal. Then
   remove `status: triage`. Expect nothing.
4. Open B. Add `blocked`. Add `status: ready for dev`. Record what the unlock is refused as; the
   design page says `itemBlocked`.
5. Open C. Expect the welcome and the lock, and no label write.
6. Open D from the no-access account. Once locked, from that account: try to comment, try to
   react, try to edit the title and the body. Record which GitHub allows.
7. Read each locked issue at `GET /repos/{owner}/{repo}/issues/{number}` and record
   `active_lock_reason`: the App sends no reason, so it should be `null`.

Reversal: unlock B and D by hand, close all four, restore the configuration.

## Expected result

Steps 1, 2, 3 and 5 match the capability's verified-by table. Step 4 documents the limit the
design page states rather than changing it. Step 6 answers the open question either way and feeds
the phase 3 design: if the author cannot edit while locked, a needs-more-information outcome must
unlock before it asks.

## Migration after evidence

1. Cite the run against the matching rows of the design page's verified-by table.
2. If step 6 shows the author can edit while locked, note it in the design page's limits; if not,
   phase 3's first line is the unlock.
3. Any belief this run changes earns a register row; the run itself does not.

## What this run found

- The open path works live, in the order designed: label, welcome, then lock, from one delivery,
  and a redelivery is a `deliveryDuplicate` with zero writes.
- **No label can release the lock on today's platform.** Beside a stale triage label the
  release is refused by rule 4, the two-position conflict. On a clean position it passes the
  decision and is refused at the apply gate by rule 5: the applier's externals carry no cause
  fingerprint (`packages/runtime/src/shell/compose/live.ts`, a comment names it a known
  over-refusal), so the person's own `labeled` event, dated the same second as `updated_at`,
  ties with the write it caused, and ties go to the human (D33). The decision-time refusal at
  18:48 with adjacent-second events is recorded and not explained; the apply-time refusal alone
  is sufficient.
- An issue opened already carrying the triage label is refused the welcome and the lock by the
  same rule: its label event is dated after the payload's `updated_at`.
- `blocked` beside a conflict never reaches `itemBlocked`; rule 4 answers first.
- The deliveries 6.15 cites appear on this App's hook, so 6.15's App id is misrecorded.

## What migrated

1. D207: a label cannot release the triage lock until the apply gate carries the cause.
2. The design page's limits and verified-by table now say what the platform refuses, citing this run.
3. Step 6 stays open, and the platform fix — the cause fingerprint or the evaluation time at the
   apply gate — is the first line of phase 3.
